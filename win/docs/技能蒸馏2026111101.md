## 0. 摘要（TL;DR）

不存在一个「装了就自动写好最简路径文档」的 agent/插件。可靠做法是把能力拆成三层并用 OpenCode 现有机制拼起来：

1. **采集（Capture）**：只在关键节点记录三类内容——非显然失败、设计取舍、状态变更。
2. **蒸馏（Distill）**：里程碑时合并去重、把具体问题升华成通用规则，重写成**可执行** RUNBOOK。
3. **验证（Verify）**：在干净目录按 RUNBOOK 跑一遍，跑通才标记 verified。

落地形态（本仓库已实施）：

```
AGENTS.md                       常驻约定（硬约束 + 记忆闭环）
docs/STATE.md                   当前架构/布局/环境约束
docs/DECISIONS.md               ADR（为什么这样选）
docs/PITFALLS.md                坑位库（症状→根因→修复→验证）
docs/RUNBOOK.md                 最小路径（可执行）
docs/VERIFY.md                  验证记录与待验证项
.opencode/skills/project-journal/SKILL.md     记录模板与硬规则
.opencode/commands/{pitfall,journal,distill,verify-runbook}.md   四个触发器
.opencode/agents/chronicler.md  只写 docs、不碰代码的子代理
```

日常只需要记 4 条命令：`/pitfall`、`/journal`、`/distill`、`/verify-runbook`。

## 1. 原始需求

### 1.1 初始问题（原文）

> 有没有一种 agent 差距，可以把我的项目中的内容都记录下来，不停的完善和修正，到项目完成时，能给出一个最简路径实现的全过程文档或者流程的记录，这样，我下次重新改项目的流程会顺畅或者从零开始做类似项目的时候，可以大量借鉴已完成工作，少走弯路

### 1.2 专业表述（Q2 的回答，四种粒度）

#### ① 一句话（评审/立项用）

> 我希望引入一层**项目级持久记忆与知识蒸馏能力**（project-level persistent memory & knowledge distillation）：持续采集开发过程中的会话轨迹、架构决策与失败模式，将其收敛为结构化、可溯源、可验证的项目知识，并在里程碑自动合成一份**可执行的最小路径运行手册（executable runbook）**，以降低后续变更的回归成本，并支持同类项目的跨项目复用。

英文版：

> I'm looking for an agentic workflow with **persistent project memory**: continuously capture session traces, design decisions, and failure modes; **consolidate** them into structured, provenance-linked, verifiable knowledge; and **synthesize an executable minimal-path runbook** at each milestone — to accelerate future changes and cross-project bootstrapping.

#### ② 结构化需求（PRD / issue 风格）

- **能力缺口（capability gap）**：agent 具备单会话推理与执行能力，但缺少**跨会话、跨项目的长期记忆**与**知识蒸馏层**；过程信息随会话丢失，导致重复踩坑、重复调研、流程知识无法沉淀与迁移。
- **目标**：构建「采集 → 蒸馏 → 合成 → 验证 → 复用」的自改进闭环（self-improving loop），把一次性开发过程转化为**可复用的程序性知识（procedural knowledge）**。

| 能力 | 说明 | AI 术语 |
| --- | --- | --- |
| 持续采集 | 自动/半自动记录会话、命令、报错、决策 | episodic memory / session telemetry |
| 知识蒸馏 | 去噪、去重、归纳、升级为通用规则 | memory consolidation / distillation |
| 产物合成 | 生成 ADR、坑位库、runbook、验收清单 | artifact synthesis |
| 可执行验证 | 每条路径都有可运行命令与验收标准 | executable spec / acceptance test |
| 检索与复用 | 按 context 召回，跨项目迁移 | RAG grounding / skill reuse |
| 溯源与保鲜 | 结论可回溯到 commit/会话；过期可标注 | provenance / staleness |

- **产出物**：`STATE.md`、`DECISIONS.md`、`PITFALLS.md`、`RUNBOOK.md`、`VERIFY.md`、索引。
- **质量属性**：低噪声（signal-to-noise）、可溯源、幂等更新、去重、防幻觉（结论必须经验证）、人机协同（human-in-the-loop）、可移植。
- **验收标准**：① 干净环境按 RUNBOOK 一次复现；② 每步可执行可校验、失败有分支；③ 知识点可溯源到 commit/文件行；④ 同类新项目可复用 ≥80% 的 runbook 与坑位库。

#### ③ 可直接作为 prompt 的版本

> 你是一个**项目知识管家（project knowledge steward）**，具备长期记忆与知识蒸馏职责。
> **采集**：在以下时机把信息结构化写入 `docs/`：做出非显然取舍（→ ADR）、遇到非显然失败（→ 失败模式条目，含症状/根因/修复/预防/验证命令）、发生结构变更（→ 状态文档）。
> **蒸馏**：里程碑时读取 `docs/` + `git log`，去重、归纳、标注过期项，把情景性记录升级为通用规则。
> **合成**：输出可执行的 `RUNBOOK`（编号步骤 + 每步验证命令 + 失败分支），并生成/更新 `VERIFY`。
> **约束**：结论必须可溯源（commit/文件:行/会话）；不确定的标注"未验证"；不写入密钥；不修改业务代码。
> **目标**：让下一次变更可快速回归，让同类项目可从零复用。

#### ④ 术语对照（原话 → 专业表述）

| 你的说法 | 专业术语 |
| --- | --- |
| 把项目内容都记录下来 | project-level persistent memory / episodic capture |
| 不停完善和修正 | memory consolidation / iterative refinement |
| 最简路径实现的全过程文档 | executable runbook / minimal-path SOP |
| 下次改流程更顺畅 | faster regression / change enablement |
| 从零做类似项目可借鉴 | cross-project transfer / skill & procedure reuse |
| 少走弯路 | reduce search cost / avoid repeated failure modes |
| （隐含）不瞎编 | provenance-linked, verified knowledge / hallucination guard |

## 2. 结论：有没有现成的 agent / 插件？

**没有开箱即用的单一方案。** 但有两条现实路径：

1. **纯人工约定**：你自己维护 `docs/`（可行，但会烂尾）。
2. **机制化（推荐）**：用 OpenCode 的 skills / commands / agents 把「何时记、怎么记、何时蒸馏、怎么验证」固化成可触发的流程。

### 2.1 为什么不能只靠"全程录制 + 自动总结"

| 想法 | 问题 |
| --- | --- |
| 把会话全存下来 | 噪音大：死胡同、试错、重复命令占 90%，无法直接当文档 |
| 让 agent 自动总结 | 会漂移/幻觉；"最简路径"一旦没验证就是误导 |
| 只在最后写一次文档 | 细节已丢，只剩"看起来对"的流程 |

### 2.2 可复用的既有组件（调研结果）

| 组件 | 作用 | 备注 |
| --- | --- | --- |
| `AGENTS.md` | 常驻项目约定（每次会话自动读） | 放"硬约束"最合适 |
| `skills` | 按需加载的流程知识 | 放"怎么写日志/怎么蒸馏" |
| `commands` | 可复用的提示模板（`/name`） | 触发器的正确位置 |
| `agents`（subagent） | 角色隔离（chronicler / reviewer） | **干净上下文**是关键 |
| `plugins` | 事件钩子，自动采集 | 需要写一点 TS（可选） |
| `opencode-sesh` | 会话浏览/检索/恢复 | 事后翻查 |
| `@openviking/opencode-plugin` | 记忆/RAG | 跨项目复用 |
| ADR / RUNBOOK / POSTMORTEM | 行业通用文档形态 | 不依赖任何 agent，可迁移 |

## 3. 方案设计

### 3.1 闭环

```
        ┌──────────── 日常开发（主 agent）────────────┐
        │  踩坑 / 做取舍 / 结构变更                     │
        └───────┬───────────────┬────────────────────┘
                │ /pitfall      │ /journal
                ▼               ▼
        docs/PITFALLS.md   docs/DECISIONS.md     ← 增量、结构化、可溯源
                │               │
                │  里程碑 /distill
                ▼               ▼
        docs/RUNBOOK.md  +  docs/STATE.md  +  docs/VERIFY.md   ← 蒸馏产物
                │
                │ /verify-runbook（干净目录执行）
                ▼
        验证通过 → RUNBOOK 标记 verified → 下次变更/新项目直接复用
```

### 3.2 角色与职责

| 角色 | 职责 | 关键点 |
| --- | --- | --- |
| 主 agent | 干活、在关键节点触发命令 | 不依赖它"自觉"记录 |
| `chronicler`（subagent） | 只写 `docs/`，不碰代码 | 干净上下文，避免被本次会话带偏 |
| skill `project-journal` | 定义"记什么/怎么记/去重" | 被 chronicler 加载 |
| 4 个 command | 触发器 | `/pitfall` `/journal` `/distill` `/verify-runbook` |

### 3.3 文件清单（OpenCode V2 规范路径）

- 技能：`.opencode/skills/<id>/SKILL.md`（**复数** `skills`）
- 命令：`.opencode/commands/<name>.md`（`/name`，body 即模板）
- 子代理：`.opencode/agents/<name>.md`（frontmatter `mode: subagent` + `permissions`）

```
AGENTS.md
docs/{STATE,DECISIONS,PITFALLS,RUNBOOK,VERIFY}.md
.opencode/skills/project-journal/SKILL.md
.opencode/commands/{pitfall,journal,distill,verify-runbook}.md
.opencode/agents/chronicler.md
```

### 3.4 记录模板（要点）

- **PITFALLS**：`PIT-NNN` + 症状 / 触发 / 根因 / 修复（命令或 `文件:行`）/ 预防 / 验证（可执行）/ 首次发现；相同根因只追加"再次出现"。
- **DECISIONS（ADR）**：`ADR-NNN` + 状态 / 背景 / 备选（≥2，写代价）/ 决定 / 后果（含代价）/ 验证。
- **RUNBOOK**：编号步骤；每步 `命令 / 期望输出 / 失败分支（引用 PIT-NNN）`；命令必须可直接执行；不确定标"未验证"。
- **STATE**：架构 / 布局 / 环境约束 / 当前状态 / 已知限制 / 文档索引。
- **VERIFY**：验收标准 + 验证矩阵（日期/版本/场景/结果/证据）+ 待验证项。

### 3.5 skill 内容（`project-journal`，已落地）

```markdown
---
name: Project Journal
description: Record reusable project knowledge into docs/ (pitfalls, ADRs, state, runbook) with provenance and executable verification. Use when a non-obvious failure happens, when a design trade-off is made, or when a milestone is reached.
---

# Project Journal

把「一次性的过程」变成「可复用的知识」。只记三类内容，**不记流水账**。

## 何时记录
| 触发 | 写到 | 编号 |
| 非显然的失败 | docs/PITFALLS.md | PIT-NNN |
| 结构/流程取舍 | docs/DECISIONS.md + docs/STATE.md | ADR-NNN |
| 里程碑（一版能跑通） | RUNBOOK + VERIFY | 时间戳/版本 |

## 格式
（PIT：症状/触发/根因/修复/预防/验证/首次发现；ADR：状态/背景/备选/决定/后果/验证；RUNBOOK：命令/期望/失败分支）

## 硬规则
1. 只写结论；过程只保留能复现问题的最短路径
2. 去重：相同根因只更新"再次出现"
3. 可溯源：文件:行 / commit / 日期 / 版本
4. 可执行：验证命令必须能跑
5. 脱敏：不写密钥；路径用相对路径或 <dir>
6. 不改业务代码；只写 docs/

## 反模式
❌ 只写"已修复"不写根因  ❌ 贴整段会话  ❌ "按需调整"  ❌ 结论没有验证命令
```

### 3.6 四个 command（已落地）

`pitfall.md`

```markdown
---
description: Record a non-obvious failure into docs/PITFALLS.md
agent: chronicler
subagent: true
---
把这次（或 `$ARGUMENTS` 描述的）非显然失败记录到 `docs/PITFALLS.md`。
1. 先读文件；相同根因只追加"再次出现"，不新建编号
2. 填：症状/触发/根因/修复/预防/验证/首次发现
3. 修复给命令或 文件:行；验证必须可直接执行
4. 只写结论；不写密钥；不改业务代码
只回复：新增/更新 <ID>：<一句话摘要>
```

`journal.md`

```markdown
---
description: Record a design decision as an ADR and update docs/STATE.md
agent: chronicler
subagent: true
---
把 `$ARGUMENTS` 描述的取舍写成 ADR 追加到 docs/DECISIONS.md，并更新 docs/STATE.md。
- 编号 ADR-NNN；若推翻旧条目，旧条目改 superseded 并注明被谁取代
- 字段：状态/背景/备选(≥2)/决定/后果(含代价)/验证
- 不改业务代码；不写死绝对路径
只回复：ADR-NNN：摘要；STATE 更新：<小节列表>
```

`distill.md`

```markdown
---
description: Consolidate docs into an executable runbook (milestone distillation)
agent: chronicler
subagent: true
---
做一次知识蒸馏：读 STATE/DECISIONS/PITFALLS + `git log --oneline -30`。
1. 去重合并（PIT 合并保留最小编号；被取代的 ADR 标 superseded）
2. 升华：反复出现的问题 → 一条通用规则（写明适用范围）
3. 重写 RUNBOOK：命令/期望输出/失败分支（引用 PIT-NNN）
4. 更新 STATE 与 VERIFY
5. 不编造步骤；不写密钥；不改业务代码
只回复：变更摘要 + 仍待验证项
```

`verify-runbook.md`

```markdown
---
description: Execute docs/RUNBOOK.md in a clean directory and report gaps
agent: general
subagent: false
---
在干净目录（`$ARGUMENTS`，默认 %TEMP%\runbook-verify-<yyyyMMdd-HHmm>）按 RUNBOOK 逐条执行。
- 不改现有仓库；产物写验证目录
- 每步记录：命令/退出码/关键输出；失败即停，说明"哪一步/为什么/走哪个分支（PIT-NNN）"
- 结束输出：通过率、耗时、与 RUNBOOK 不一致需更新的条目
- 不给文档写密钥；VERIFY 只追加一行摘要
```

```markdown
    effect: allow

    resource: "*"
    effect: allow

    resource: "*"
    effect: allow
  - action: shell
    resource: "git *"
    effect: allow
---
你是本项目的知识管家。只维护 docs/，绝不修改代码。

写之前先读现有文件，保持编号连续、格式一致。
完成后用一行摘要说明改了什么。
```

## 5. 怎么用（让方案生效）

| 场景 | 你做什么 | 会发生什么 |
| --- | --- | --- |
| 又踩了一个坑 | `/pitfall 429 限流` | chronicler 写 `PITFALLS.md`，返回 `PIT-00x` |
| 改了架构 | `/journal 把 env 改成相对路径` | 新增 ADR + 更新 STATE |
| 一版跑通了 | `/distill` | 合并去重、重写 RUNBOOK/STATE/VERIFY |
| 想确认文档没骗人 | `/verify-runbook` | 在临时目录按 RUNBOOK 跑，报告不一致 |
| 新项目复用 | 复制 `AGENTS.md` + `docs/` + `.opencode/`，只改 STATE/RUNBOOK 的路径与版本 | 立即具备同样的工作流 |

## 6. 怎么验证"生效了"（L0–L7）

| 层 | 验证动作 | 期望结果 |
| --- | --- | --- |
| L0 | 新开会话看是否读到 `AGENTS.md` | 会话里体现其硬约束（如 CL 禁用清单） |
| L1 | 输入 `@project-journal` | 技能被加载 |
| L2 | 输入 `/` 看命令列表 | 出现 `pitfall/journal/distill/verify-runbook`；没有则 `/reload` |
| L3 | `opencode debug agents` | 输出含 `chronicler` |
| L4 | `/pitfall 测试：故意写一条` | `git status` 出现 `M docs/PITFALLS.md`，新增 `PIT-0xx` 且字段齐全 |
| L5 | 再发一次同样的 `/pitfall` | 编号不变，只多一行"再次出现" |
| L6 | `/distill` | RUNBOOK 变为编号步骤+验证命令；重复条目被合并；输出"待验证项" |
| L7 | `/verify-runbook` 或手工按 RUNBOOK 在新目录跑 | 每步有退出码；失败能定位到步骤与 PIT 编号；通过后 RUNBOOK 标 verified |
